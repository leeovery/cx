- FINDING: Commit-time slot load re-resolves what the same keypress already resolved, and gates the in-force light/dark answer on it
  SEVERITY: medium
  FILES: internal/tui/theme_panel_confirm.go:139, internal/tui/theme_panel_confirm.go:190, internal/tui/theme_panel_commit.go:344, internal/tui/theme_seams.go:32, internal/theme/resolution.go:200
  DESCRIPTION: On a confirmed `d`/`l` over a constant the panel resolves the newly-live slot twice in one keypress. `commitSlot` → `recomputeThemePanel` → `applyCommittedSetting` calls `ThemeSource.Resolve`, which — the mirrored keys now describing a pair — resolves *both* slots against the retained enumeration and hands back a `Resolution` whose `Slots` already contain the newly-live slot's record. `loadNewlyLiveSlot` then calls the seam's fourth method, `ThemeSource.ResolveSlot`, on that same slot against that same enumeration, and discards the returned `SlotResolution` entirely, keeping only the error. The method therefore exists on the seam purely for an emission side effect (the commit-cadence `theme: loaded`), while the record it produces is already in hand one call earlier. Two consequences follow. First, `themeState.canvasMode` — the answer that decides which member `Esc` resolves to — is assigned only if that throwaway resolution succeeds, coupling the retained OSC 11 classification (a fact about the terminal) to whether an unrelated palette loaded; on the failure path the model silently keeps the pre-conversion dark answer. Second, correctness rests on a four-part ordering contract restated in the call site's comment ("after a write that landed", "past commitSlot's own mirror and recompute", "never on the nil-persister path", "nothing renders between the two") plus an explicit re-read of the persister to distinguish "wrote nothing" from "write failed" — caller discipline where the design could carry the rule itself.
  RECOMMENDATION: Resolve once per commit and announce from the record already held: give `applyCommittedSetting`'s resolution the commit cadence for the one slot that is newly live (the `resolutionPass` in internal/theme already models cadence as a value), and set `canvasMode` from `retainedCanvasAnswer()` unconditionally on the conversion rather than behind a second resolution's error. That also drops `ResolveSlot` from `ThemeSource`, bringing the seam to three methods — in line with the project's 1–3-method interface convention and with what every fake (internal/capture, the tui test fakes) has to answer for — and collapses the four-part ordering contract to one.

- FINDING: `themeState.nomination` is maintained past construction with no production reader
  SEVERITY: low
  FILES: internal/tui/theme_panel_commit.go:344, internal/tui/model.go:1387, internal/tui/model.go:1404, internal/tui/theme_state.go:20
  DESCRIPTION: The nomination's only production readers are `hasNomination` and `syncResolvedMode`, and `syncResolvedMode` runs only from `New`, `armAppearanceDetection` and gate transitions — all of which complete before a panel can exist (the gate resolves before first paint, and `t` is unbound on the loading page; a pinned constant gate refuses every later resolution outright). `applyCommittedSetting` nevertheless re-derives and stores the nomination on every successful commit, and error-gates that store so a failed resolution leaves it alone. The result is a write-only field: a second description of the persisted setting held beside `themeState.keys`, from which `themeSetting()` and every panel path actually derive what they use. It is cheap, but it is a state mirror with no runtime consumer to keep it honest — precisely the shape that drifts unnoticed and is then trusted the day a reader appears.
  RECOMMENDATION: Drop the commit-time nomination write and let the field stay what its own doc calls it — the injected construction-time value — with the keys plus the retained enumeration remaining the single source the panel derives from. If a future reader genuinely needs the persisted setting's palettes, derive them at that site from the keys rather than keeping a stored copy in step.

- FINDING: `prefs.ThemeKeys` → `theme.RawKeys` crosses the boundary as three positional same-typed strings, at two independent sites
  SEVERITY: low
  FILES: cmd/open.go:804, cmd/doctor_theme.go:233, internal/theme/setting.go:37
  DESCRIPTION: `theme.NewRawKeys(theme, light, dark string)` takes three adjacent parameters of the same type, and both boundary crossings spell out `keys.Theme, keys.Light, keys.Dark` from a struct whose fields already carry exactly those names. Nothing in the type system prevents transposing light and dark, and a transposition would invert the adaptive pair for TUI construction, or mislabel doctor's `(light)`/`(dark)` parenthetical, with every palette still loading and no test outside the specific slot-label assertions failing.   SEVERITY: low

  DESCRIPTION: `NewSilentLoader()` exists precisely so "this caller writes nothing" is an explicit, greppable decision ("a constructor rather than a shape each assembles for itself"), yet `NewLoader(nil)` produces a behaviourally identical loader — the nil `*EventLogger` is a valid silent seam — and that is what production reaches for in `internal/tui/builtin_themes.go`.
