- FINDING: The forced-close geometry flash is never scheduled to auto-clear
  SEVERITY: medium
  FILES: internal/tui/theme_panel.go:260-277, internal/tui/model.go:1478-1480
  DESCRIPTION: §14A pins six theme signals and states that "All six theme signals route through the **transient flash** slot". In Portal a transient flash is defined by `flashAutoClearDuration` + a scheduled `flashTickCmd` (internal/tui/sessions_flash.go:27-39); every other theme flash obeys that — `blockThemePanel` returns `flashTickCmd(m.flashGen)` for the three entry-refusal strings, and `reportOutstandingCommitFailure` returns one for `theme not saved — see portal.log`. The resize-below-floor arm does not. In `resizeThemePanel`, when no commit failure is outstanding, `closeThemePanel()` returns nil, `m.setThemeFlash(themePanelForcedCloseFlash(dim))` raises the band, and the function returns that nil — so `Update`'s `if closed := (&m).resizeThemePanel(); closed != nil` batches nothing. `terminal too narrow — theme picker closed` / `terminal too short — theme picker closed` therefore persist indefinitely rather than for ~3s, clearing only on the next actionable keypress or when another flash supersedes them. This is the one arm of the theme flash surface that is not transient, and it is the arm reached by an ordinary window resize. The geometry tests (internal/tui/theme_panel_geometry_test.go:230-243, internal/tui/theme_panel_entry_test.go:364) assert the flash *text* only, so nothing covers the missing tick.
  RECOMMENDATION: In `resizeThemePanel`'s refusal arm, when `!willReport`, return `flashTickCmd(m.flashGen)` (captured after `setThemeFlash` bumps the generation) instead of the nil `cmd`, batching it with `cmd` if both were ever to be non-nil. Add an assertion to the forced-close tests that the returned command is a flash tick, matching the entry-refusal path's coverage.

- FINDING: §14A's band-precedence change for theme flashes is encoded as a tier that cannot change any outcome
  SEVERITY: low
  FILES: internal/tui/notice_band.go:235-250, internal/tui/sessions_flash.go:18-25, internal/tui/model.go:1330-1345
  DESCRIPTION: §14A decides "**The filter line is the one contender above flash that can be live throughout a panel open/use/close, and the theme flashes take precedence over it**", naming it a change to the band's precedence. The implementation adds `flashOrigin` (`flashOriginDefault` / `flashOriginTheme`), `setThemeFlash`, `themeFlashClaim` and `flashSlotClaim` to express that tier — but the model holds a single `flashText`, so `themeFlashClaim` and `flashClaim` return the same value whenever a theme flash is live, and `flashSlotClaim`'s two arms are functionally identical. The filter line is also not a contender for this slot at all: it is rendered on the list's title row by `applySectionHeader` (internal/tui/model.go:3326-3376), a different physical row from `renderSessionBandSlot`. The *required behaviour* holds — a theme flash always reaches the band regardless of filter state — but it holds structurally, not because of the tier. The risk is that the code documents ("Do not re-order") an arbitration that does not exist, so a future change to the band that genuinely introduces the filter line as a contender will believe it is already protected.
  RECOMMENDATION: Either keep the machinery and correct the comments to say the tier is a forward guard whose ordering is currently unobservable (and add a test that pins *why* — that the filter line renders on the section-header row, so the flash slot is unconditional), or drop `flashOrigin`/`themeFlashClaim`/`flashSlotClaim` and record the conformance argument (`filter line ≠ band contender`) in one comment on `activeNoticeBand`. Do not leave a no-op mechanism carrying a "do not re-order" warning.

- FINDING: Panel header renders the `border` rule above the `Themes` label, inverting §9.1's stated order
  SEVERITY: low
  FILES: internal/tui/theme_panel_render.go:31-38, internal/tui/theme_panel_geometry.go:41-67
  DESCRIPTION: §9.1 pins the panel header as "The label is **`Themes`**, rendered in `accent.mode` ... followed by a one-row `border` rule, matching the Sessions section-header idiom minus the count." `themePanelHeaderBlock` writes the rule at `shape.ruleRow` and the label at `shape.labelRow`, and both shapes put the rule first (compact: rule row 0, label row 1; page-aligned: rule at the page's `headerBand` height, label at the page header block's height). The rendered capture confirms rule-then-label. The implementation's own comment gives the reason — the rule shares the page's rule lane and `Themes` then aligns with `Sessions ··· N` — which is what the spec's own "matching the Sessions section-header idiom" clause actually describes, and a reference frame for the revised chrome was exported (`testdata/vhs/reference/theme-panel-chrome-revision-mv.png`). So the two halves of §9.1's sentence disagree and the code followed the idiom clause rather than the sequence clause. Flagged only because it is a pinned layout statement the code now contradicts on its face, with nothing in the spec recording the resolution.
  RECOMMENDATION: No code change — the alignment reading is the correct one and is already justified in-source. Record the resolution (header is rule-then-label, aligned to the page's rule lane and section-header row) where the sequence claim would otherwise be re-read as authoritative, so a later reviewer does not "fix" the order back.

SUMMARY: The implementation tracks the specification closely across the loader ladder, the reason vocabulary, the union/badge/sort rules, prefs RMW and migration semantics, the doctor advisory class, export copy and exit codes, the log event catalogue and attr keys, and the guard-test reshape; the built-in `.theme` values match §7.3/§7.4 exactly and the retired vocabulary is fully gone. One real conformance gap: the resize-forced-close flash is raised without a `flashTickCmd`, so two of §14A's six "transient" theme signals are not transient. The other two findings are documentation/mechanism hygiene rather than behavioural drift.
