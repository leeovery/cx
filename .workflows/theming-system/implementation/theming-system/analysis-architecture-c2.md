- FINDING: The "which persisted theme keys are in force" rule is authored twice — once in internal/theme, once in cmd/doctor
  SEVERITY: medium
  FILES: internal/theme/union.go:383, cmd/doctor_theme.go:259
  DESCRIPTION: Both the panel's union assembly (`inForceValues`) and doctor's persisted-theme producer (`persistedThemeNominations`) answer the same question — given the three raw keys, which values is Portal actually reading? — and both must agree, because the panel row set and doctor's advisory block are specified to report the same problems ("one slug is one row" / "one slug is one line"). Only *half* the rule is shared: both call `ResolveSetting` for the `theme`-wins tiebreak, but each then independently re-implements "only non-empty raw slots contribute" and "two slots naming the same value collapse to one". `inForceValues` is unexported, so doctor structurally cannot compose on it and had to re-author it; the two agree today by inspection alone. There is also no cross-surface parity test — every test pins one surface against hand-written expectations, so a change to one side's collapse or emptiness rule fails nothing on the other. This is the composition case the spec itself calls out ("Doctor's persisted line makes the identical call for the identical reason, so the two surfaces cannot disagree").
  RECOMMENDATION: Export one in-force selection from internal/theme — e.g. `InForceSlots(keys RawKeys) []struct{Value string; Slot Slot; Both bool}` (or a small named type) — beside `ResolveSetting`, and derive both `inForceValues` and doctor's nominations from it; doctor keeps only its slot-label rendering. Add one parity test asserting the panel union's persisted rows and doctor's persisted lines name the same slug set for a shared table of key shapes.

- FINDING: The commit path mirrors prefs' write semantics in memory, and nothing binds the mirror to what is actually written
  SEVERITY: medium
  FILES: internal/tui/theme_panel_commit.go:131, internal/tui/theme_panel_commit.go:310, internal/prefs/store.go:436, internal/prefs/store.go:458, cmd/open_theme_commit_test.go:213
  DESCRIPTION: A commit writes through the persister and then re-states the same mutual-exclusion rules in memory so the panel can recompute rows and badges: `commitConstant` sets `RawKeys{Theme: slug}` (constant clears both slots) and `mirrorThemeSlot` sets one slot and drops the constant while carrying the other slot across. Those are exactly the rules `prefs.SaveTheme` / `SaveThemeSlot` apply to the file. The two implementations are only ever checked in isolation: `internal/tui`'s commit tests inject a fake persister and assert the mirrored keys against literals, while `cmd/open_theme_commit_test.go` asserts the bytes on disk but never the post-commit panel state. Nothing fails if they drift — and the failure mode is precisely the invariant the panel is built around: the `●` badge claiming a persisted state the file does not hold, with no other surface to contradict it until relaunch. (Full single-sourcing is blocked by the prefs leaf rule — prefs cannot import internal/theme — so the fix is a shared statement on the TUI side plus a binding assertion, not one shared mutator.)
  RECOMMENDATION: Express the in-memory transformation once as a method on `theme.RawKeys` (`WithConstant(slug)` / `WithSlot(slot, slug)`) that the commit handlers call, and extend one of the existing cmd round-trip tests to assert the model's post-commit keys (or rendered badges) equal `prefsStore.LoadThemeKeys()` read back from disk — one assertion that makes the two layers provably agree.

- FINDING: Three parallel light/dark enumerations, with the persistence enum carried through panel state
  SEVERITY: low
  FILES: internal/prefs/store.go:177, internal/theme/resolution.go:12, internal/theme/member.go:17, internal/tui/theme_panel_confirm.go:250, internal/tui/theme_panel_commit.go:310, cmd/theme_persister.go:111
  DESCRIPTION: The light/dark distinction is modelled three times — `theme.Slot` (3-valued, includes constant), `theme.Member` (2-valued, zero = dark) and `prefs.ThemeSlot` (2-valued, zero invalid). Each is individually justified (prefs is a leaf and cannot use `theme.Slot`), but the *persistence* type is the one threaded through the panel: `themeSlotConfirm.slot`, `handleSlotCommitKey`, `commitSelectedSlot`, `commitSlot` and `mirrorThemeSlot` all carry `prefs.ThemeSlot`, and it is converted back to domain types at three sites (`oppositeThemeMember`, the switch inside `mirrorThemeSlot`, and `cmd`'s `themeSlotFor`). That is the wrong direction of travel for a layer boundary: the domain owns light/dark, the store is the edge. It also produces one silent arm — `themeSlotFor`'s `default` maps an out-of-range slot to `SlotConstant`, so an invalid slot would log a commit failure with no `slot` attr rather than being impossible.
  RECOMMENDATION: Hold `theme.Slot` (or `theme.Member`) in the panel and convert exactly once, at the persister seam — either by having `ThemePersister.CommitThemeSlot` take the domain slot and letting the cmd adapter map it to `prefs.ThemeSlot`, or by mapping at the single call into the persister. That deletes two of the three conversions and removes the default arm.

- FINDING: `AdaptivePair` can silently build a half-empty nomination
  SEVERITY: low
  FILES: internal/theme/nomination.go:78, internal/theme/nomination.go:86
  DESCRIPTION: `AdaptivePair(a, b MemberPalette)` folds its two arguments through `hold`, which assigns by the tag each palette carries. The tagging prevents a swapped pair, but it does not prevent two palettes tagged with the *same* member: `AdaptivePair(MemberLight.Palette(x), MemberLight.Palette(y))` compiles, leaves `dark` as the zero `Theme`, and `Select(MemberDark)` then returns a palette whose every value resolves through `lipgloss.Color("")` — a silently colourless render, the exact failure mode `defaultDarkTheme` exists to prevent elsewhere. Both current callers are provably safe (one uses the constants directly, one uses `m` and `m.Opposite()`), so correctness rests on caller discipline rather than on the constructor.
  RECOMMENDATION: Make the invalid pair unconstructible or loud — either take the two halves as distinct parameters internally (`pairFor(light, dark Theme)`) with a thin `Member`-driven wrapper for the dynamic caller, or have `AdaptivePair` fall back to a defined half (or panic in the impossible case) when both arguments name the same member.

- FINDING: `themeState.nomination` becomes write-only after the gate resolves, and is maintained on only one of the two commit paths
  SEVERITY: low
  FILES: internal/tui/theme_state.go:35, internal/tui/model.go:1351, internal/tui/model.go:1406, internal/tui/theme_panel_confirm.go:235
  DESCRIPTION: The nomination is read in exactly two places, both inside the appearance gate's lifecycle (`newNominationGate` at arm, `Select` in `syncResolvedMode`), and the gate resolves once before first paint. After that nothing reads the field. The constant-commit path leaves it holding the pre-commit pair; the constant→adaptive conversion rebuilds it from the newly-loaded slot and the currently *previewed* palette. So the field is stale on one path, freshly written-but-unread on the other, and the commit-time slot load's only production effect is its `theme: loaded` line plus the `canvasMode` update beside it. Nothing is wrong today, but a future reader of `nomination` (a re-detect, a second gate arm) would get a half-truth from either path, and the asymmetry gives no signal about which one is intended to be authoritative.
  RECOMMENDATION: Pick one contract and make it structural: either treat the nomination as construction-time-only input (drop the assignment in `loadNewlyLiveSlot`, keeping the load for its event and the `canvasMode` update) or maintain it on both commit paths so the field always describes the current setting. Whichever is chosen, state it on the field so a later reader knows whether it may be trusted post-gate.
SUMMARY: The theming implementation composes well overall — the loader/assembler/resolution split in `internal/theme` is clean, the `ThemeEnumerator` seam correctly returns the finished union so the TUI does no merging, the restyle path is single-sited and behaviourally guarded, and the leaf/logging constraints hold everywhere. The two findings worth acting on are both cross-layer agreement gaps: the in-force key rule is authored twice (panel vs doctor) with no parity test, and the commit path's in-memory key mirror re-states prefs' write semantics with nothing binding the two together.
