- FINDING: `portal doctor` re-resolves persisted theme slugs off the filesystem instead of the enumeration it just took
  SEVERITY: medium
  FILES: cmd/doctor_theme.go:134-138, cmd/doctor_theme.go:227-242, cmd/doctor_theme.go:312-323, cmd/doctor_theme.go:355-372, internal/theme/resolution.go:173-175, internal/theme/resolution.go:284-295
  DESCRIPTION: Doctor's theme block runs two independent producers over the same directory. `scanThemesDirectory` calls `loader.Enumerate(dir)` — one ReadDir plus one parse per candidate — and then `persistedThemeAdvisories` calls `loader.ResolveByName(slug, themesDir)` once per in-force key, which stats the directory again and re-reads and re-parses a file the enumeration parsed moments earlier. `internal/theme` already owns the primitive that avoids this: `ResolveNominationFrom` / `entryResult` resolve a slug against a *retained* `Enumeration` with no I/O, and it exists precisely because a second parse of the same slug "is free to disagree with the row the user is looking at" (resolution.go:155-157). Doctor is the one surface that reintroduces that hazard: its file line for slug X comes from parse A, and its persisted line for the same slug comes from parse B, with the file line then dropped on the strength of a slug read from parse A. `assembleThemeAdvisories` additionally re-authors the union's membership rule ("a slug already listed contributes no separate entry") which `persistedRows`/`listedUnder` (internal/theme/union.go:339-354) already state — the two surfaces deliberately pick different survivors, but the membership rule itself now lives in two packages and can drift silently. The pre-existing task 12-1 fix single-sourced *which keys are in force* (`theme.InForceKeys`); it did not single-source the resolution source or the membership rule.
  RECOMMENDATION: Have doctor take one enumeration and drive both producers from it: keep `loader.Enumerate(dir)` (or `Assembler.Open`, which is silent under `NewSilentLoader`) and resolve each in-force key against that retained `Enumeration` via the existing enumeration-backed resolver rather than `ResolveByName`. Doctor's own line frames, slot labels and persisted-wins ordering stay exactly as they are; only the source of the verdict and the membership test move onto the shared value. That removes the duplicate reads, makes the two lines describe one parse, and leaves `internal/theme` the single author of "which slugs earn an entry".

- FINDING: The light/dark answer is modelled three times on the model, with the correct field to read enforced only by comments
  SEVERITY: medium
  FILES: internal/tui/theme_state.go:58-69, internal/tui/theme_state.go:96-107, internal/tui/appearance_gate.go:51-64, internal/tui/model.go:1404-1408, internal/tui/model.go:2587-2626, internal/tui/theme_panel_confirm.go:197-247, internal/tui/theme_panel.go:486-515
  DESCRIPTION: Three separate representations of "light or dark" coexist on the model: `appearanceGate.appearance` (the gate's resolution, which on a pinned/constant gate is the standing dark fallback and is explicitly *not* a fact about the terminal), `themeState.canvasMode` (the answer in force, which mirrors the gate via `syncResolvedMode` and then deliberately diverges from it after a mid-session constant → adaptive conversion), and the `bgReplyArrived`/`bgReplyDark` pair (the raw OSC 11 classification, read through `retainedCanvasAnswer`). Each of the three carries a doc comment warning which of the other two must not be substituted for it — `inForceSlot`'s "the mode read here must not be `gate.appearance`", `themeState`'s "two of its fields look like drift and are not", `retainedCanvasAnswer`'s "not read off the gate". The divergence is currently safe only because a pinned gate can never re-resolve, so `syncResolvedMode` cannot run after a conversion and clobber `canvasMode` back to dark; that is a non-local coupling between `appearanceGate.pinned`, the `BackgroundColorMsg` arm and the conversion path, holding by construction rather than by construction being visible. The result is that correctness of the converted-light-terminal case depends on every future call site picking the right one of three near-identical `theme.Member`-valued fields, with no type distinction between "what the terminal said", "what the gate resolved" and "what is in force".
  RECOMMENDATION: Collapse the three onto one owned value plus derivations. Model the terminal's reply once as an explicit optional (e.g. a small `detectionAnswer{arrived bool, member theme.Member}` fed by the `BackgroundColorMsg` arm), let the gate hold only its resolution state, and expose a single `themeState.inForceMember()` accessor that returns the gate's answer for an armed adaptive gate and the retained reply for a converted constant. Callers then have one thing to read, the "must not substitute" comments become unnecessary, and the pinned-gate coupling stops being load-bearing.

- FINDING: `theme.Loader`'s zero value compiles as a production loader but silently reserves no built-in slugs
  SEVERITY: medium
  FILES: internal/theme/load.go:19-48, internal/theme/load.go:66-87, internal/theme/union.go:205-209
  DESCRIPTION: `Loader` is an exported struct with exported `ReservedSlugs` and `BuiltinSource` fields and an unexported `events` seam. `theme.Loader{}` is therefore a legal expression at any call site in any package: it compiles, judges files through the full ladder, and reserves nothing — so a user's `tokyo-night.theme` would shadow the built-in that the per-slot fallback resolves to, which is the one property `NewLoader`'s doc calls out as needing to be impossible. `NewLoader` panics on a nil event seam specifically so silence is a readable decision at the call site, but the zero value bypasses that check entirely and fails silently rather than loudly. Nothing structural prevents the mistake: the fields are exported only so the package's own tests can drive the ladder with a synthetic reserved set (`load_test.go:60`, `union_test.go:305`, plus `internal/themetest/theme_file_test.go`), and this package already carries source-scanning guards for weaker invariants (`leaf_guard_test.go`, and the codebase-wide precedent of `restore_source_guard_test.go` / `colour_literal_guard_test.go`).
  RECOMMENDATION: Make the unsafe shape unreachable rather than documented. Either unexport `ReservedSlugs`/`BuiltinSource` behind constructors (`NewLoader`, `NewSilentLoader`, and a `themetest`-owned synthetic-set constructor for the tests that need one), or — if the exported fields must stay for test ergonomics — add a source guard in the shape the package already uses, asserting no `theme.Loader{` composite literal appears outside `_test.go` files.

- FINDING: The `ThemeSource` seam takes three different input granularities, leaving `internal/theme`'s setting rules in `internal/tui`
  SEVERITY: low
  FILES: internal/tui/theme_seams.go:32-37, internal/tui/theme_panel.go:475-478, internal/tui/theme_panel_confirm.go:197-220, internal/theme/dir_theme_source.go:40-73
  DESCRIPTION: The seam's four methods take three different shapes of the same state: `Open`/`Reassemble` take `theme.RawKeys`, `Resolve` takes an already-collapsed `theme.Setting`, and `ResolveSlot` takes a slot plus an already-*defaulted* slug. The consequence is that two `internal/theme` rules have to be applied on the TUI side before the seam can be called — `themeSetting()` re-runs `theme.ResolveSetting` to collapse the keys, and `persistedSlotSlug` switches on `theme.Slot` to pick the shipped-default-substituted slug out of the resolved `Setting`. Both are documented as having "a single site", but that site is now in the render layer rather than behind the seam, and a fake is free to answer a differently-derived setting from the one the panel lists and marks. The asymmetry buys nothing: `Reassemble` already collapses `RawKeys` internally via `InForceKeys`, so `Resolve` taking the same input would be uniform and cost nothing.
  RECOMMENDATION: Make the seam uniform in what it consumes: have `Resolve` take `theme.RawKeys` and collapse internally through `ResolveSetting`, and have `ResolveSlot` take the slot alone (or a `theme.Member`) plus the keys, resolving the slot's nominated slug through `Setting` inside `internal/theme` — e.g. a `Setting.Slug(Slot) string` accessor. The TUI then keeps `themeSetting()` only for the one thing it genuinely decides (whether `d`/`l` must raise the confirm), and no resolution or defaulting rule lives outside the package that owns it.

- FINDING: `Row.SortKey()` doubles as the row's identity for badge lookup and cursor anchoring
  SEVERITY: low
  FILES: internal/theme/union.go:92-94, internal/theme/badge.go:102-107, internal/tui/theme_panel.go:560-566, internal/tui/theme_panel_commit.go:307-320
  DESCRIPTION: `SortKey` is documented as an ordering value ("the ordering consumes SortKey ... neither may be re-derived from the other"), yet three consumers use it as the row's *identity*: `BadgeKey` returns it, `themePanelRowIndex` matches on it to place the cursor, and `previewedThemeIdentity` captures it to re-anchor after a commit. Each site carries a comment explaining that a sort key is standing in for an identity, which is the tell. The two concepts happen to coincide today (slug → filename → persisted string), but they are independent: any future change to the ordering — sorting by label, or grouping built-ins — would silently relocate the panel's cursor anchoring and badge lookup with it, and the failure mode is the invariant the panel is built around (the cursor sits on a row other than the one being painted).
  RECOMMENDATION: Name the identity separately on `theme.Row` — e.g. `Identity()` holding the slug/filename/persisted precedence — and define `SortKey()` and `BadgeKey()` in terms of it. The three consumers then depend on identity rather than on ordering, and the two can be changed independently without a silent coupling.
SUMMARY: The theming system's package boundaries are strong — `internal/theme` is a genuine leaf that resolves no paths, the loader/assembler/resolver split is clean, the panel is well-decomposed across files, and the capture seam is faked wholesale as specified. The issues that remain are seam-level: doctor re-resolves off disk instead of composing the enumeration-backed resolver that already exists, the light/dark answer has three model-level representations kept correct by comment, and a few exported shapes (`Loader`'s zero value, `ThemeSource`'s mixed inputs, `SortKey`-as-identity) rely on caller discipline where they could be structural.
