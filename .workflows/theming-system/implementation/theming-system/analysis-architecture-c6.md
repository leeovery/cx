  SEVERITY: medium

  DESCRIPTION: `internal/portalbintest` was, before this work, exactly what its package doc says it is — `ProjectRoot` / `BuildPortalBinary` / `StagePortalBinary`, i.e. compile the portal CLI and stage it on $PATH for integration tests. This implementation added three generic Go-source-scanning helpers to it (`GoSourceFiles`, `PackageGoFiles`, `ForEachFuncCall`) and now ~15 source guards across `internal/theme`, `internal/tui`, `internal/prefs`, `internal/capture` and `cmd` import that package for them. The package doc had to be amended to list a second, unrelated exported surface — the signal that the boundary moved rather than that the package grew. Because this is now the established home, every future source guard lands here too, and the package name will keep drifting further from what it holds.
  RECOMMENDATION: Move the three source-scanning helpers into a small dedicated test-helper package (e.g. `internal/sourceguard` or `internal/guardtest`) alongside their own tests, leaving `portalbintest` as the binary build/stage helper its name and doc describe. Consumers change one import path; no behaviour moves.

- FINDING: The prefs → theme key boundary is crossed positionally, at two sites, with three same-typed strings
  SEVERITY: medium
  FILES: cmd/open.go:804, cmd/doctor_theme.go:250, internal/theme/setting.go:37, internal/prefs/store.go:142
  DESCRIPTION: `prefs.ThemeKeys{Theme, Light, Dark}` and `theme.RawKeys{Theme, Light, Dark}` are field-identical mirrors, and the conversion between them is written out as `theme.NewRawKeys(keys.Theme, keys.Light, keys.Dark)` at both cmd surfaces that read prefs (TUI construction and doctor's persisted-theme producer). Three parameters of the same type in a fixed order is the one remaining place in this feature where light and dark can be transposed silently: it compiles, every palette still loads, every token still resolves, and the whole product's adaptive pairing is inverted — with doctor cheerfully labelling the slots the same wrong way. That is precisely the failure mode the rest of the implementation designs structurally against: `theme.AdaptivePair` refuses a positional light/dark pair in favour of a `MemberPalette` tag, `RawKeys.WithMember` takes a `Member` rather than a position, and `prefs.ThemeSlot` gives its zero value no name so a forgotten argument cannot write the light slot. The two conversion sites are also free to drift from each other, since nothing binds them.
  RECOMMENDATION: Give the boundary one home — a single cmd-local mapping (`func themeRawKeys(k prefs.ThemeKeys) theme.RawKeys`) that both `themeResolution` and `persistedThemeAdvisories` call, written with named fields rather than positional arguments, so the transposition is unwritable and the mapping has exactly one site.

- FINDING: `ThemeSource.ResolveSlot` is a query whose only production call reads neither return, and duplicates a resolution performed one call earlier
  SEVERITY: low
  FILES: internal/tui/theme_panel_confirm.go:196, internal/tui/theme_seams.go:42, internal/theme/dir_theme_source.go:81, internal/tui/theme_panel_commit.go:343
  DESCRIPTION: `loadNewlyLiveSlot` is the sole production caller of the seam's fourth method. It discards the `SlotResolution` deliberately (the palette is already in the nomination `applyCommittedSetting` re-resolved on the same keypress, via `Resolve` → `ResolveNominationFrom`, which loads both slots), and its error branch is a bare `return` as the function's final statement — so both arms do nothing and the call's only observable effect is the commit-cadence `theme: loaded` emission inside `internal/theme`. The result is a seam method typed as a query but used as a command: the same slug is resolved twice against the same retained enumeration on one keypress, every implementation of `ThemeSource` (production adapter, capture fake, test fakes) must answer a fourth method whose value nothing reads, and the capture fake's own doc has to explain that its honest implementation is unreachable. The emission-cadence split is sound; it is the shape of the seam that overstates what the caller wants.
  RECOMMENDATION: Narrow the seam to what the call site consumes — either have `ResolveSlot` return `error` only (or nothing) and name it for the announce-the-newly-live-slot job it performs, or fold the commit-cadence emission into the resolution `applyCommittedSetting` already performs so the fourth method disappears. Either way, drop the vacuous `if err != nil { return }` in favour of an explicit discard, so a reader is not told an error is handled when it is not.

- FINDING: The flash's precedence tier lives on `themeState` while its three co-varying siblings live on `Model`
  SEVERITY: low
  FILES: internal/tui/theme_state.go:151, internal/tui/model.go:2314, internal/tui/notice_band.go:526, internal/tui/sessions_flash.go:53
  DESCRIPTION: `flashText`, `flashGen` and `flashKind` are `Model` fields; `flashOrigin` — a fourth attribute of the same single live flash, with the same lifetime — was placed inside `themeState`. Two consequences follow. The generic `setFlash`, used by flash producers that have nothing to do with themes (the preview-attach bail, success flashes), must reach into the theme subsystem's state to reset a tier it does not otherwise know about; and the general notice-band arbiter resolves its precedence question by reading out of `m.themeState`, which sends a reader of the band into the theme machinery to learn how a non-theme flash is ordered. It also breaks `themeState`'s own documented charter ("the loaded setting, the seams the panel reaches it through, the light/dark resolution, and the palette every renderer paints from") with a field that is none of those. The `flashOrigin` *type* is already correctly declared beside `flashKind` in sessions_flash.go — only the field is misplaced.
  RECOMMENDATION: Move the `flashOrigin` field onto `Model` beside `flashText`/`flashGen`/`flashKind`, leaving `setThemeFlash` as the only writer of the theme tier. No behaviour changes; the flash's four attributes then live and reset in one place, and `themeState` keeps its stated scope.
SUMMARY: The theming architecture is strong — a genuinely leaf `internal/theme` owning the vocabulary, ladder, resolution and union assembly; a single four-method panel seam that keeps `internal/tui` free of path policy and of the `theme` log component; and clean cmd ownership of paths, the persister and the translation. The residue is boundary placement rather than structure: repo-wide source-guard helpers homed in the binary-build test package, a positional three-string prefs→theme key conversion duplicated at two cmd sites, a seam method whose returns nothing reads, and one flash field parked in the theme subsystem's state.
