- FINDING: `ThemeSource.ResolveSlot` is a seam method whose only production effect is a log emission
  SEVERITY: medium
  FILES: internal/tui/theme_seams.go:14, internal/tui/theme_panel_confirm.go:70-77, internal/tui/theme_panel_commit.go:104-134, internal/theme/dir_theme_source.go:34-37, internal/theme/resolution.go:82-84
  DESCRIPTION: The panel's slot-commit path runs two resolutions over the same retained enumeration. `commitSlot` → `recomputeThemePanel` → `applyCommittedSetting` calls `source.Resolve`, which (after `WithMember` has set the slot and cleared the constant) resolves *both* slots through `ResolveNominationFrom` and installs the resulting `Nomination` — so the newly-live slot's palette is already loaded and held. `confirmSlotAssignment` then calls `loadNewlyLiveSlot`, which resolves that same slot a second time via `source.ResolveSlot` and discards the returned `SlotResolution` entirely; the only observable difference between the two calls is that `ResolveSlot` reports through `reportSlot` (emitting `theme: loaded`) while `Resolve` reports through `reportFallback` (which does not).   RECOMMENDATION: Make the seam honest about what the call site needs. - FINDING: Panel fixtures hand-author the union that `internal/theme` exists to assemble
  SEVERITY: medium
  FILES: internal/capture/fixtures.go:428-436, internal/capture/fixtures.go:513-519, internal/capture/fixtures.go:552-575, internal/capture/fixtures.go:607-616, internal/capture/fixtures.go:647-655, internal/theme/union.go:132-138, internal/theme/union.go:215-233, internal/capture/theme_panel_fixture_test.go:35-75
  DESCRIPTION: Each panel fixture declares its membership twice: once as `theme.Enumeration.Entries` (via `themePanelDirEntry`) and again as a fully-formed `theme.Union` with rows written out in display order and `Count`/`Rejected` set by hand. The two declarations must agree, and nothing ties them together — `TestPanelFixture_FourInputs` only checks that the *fake* hands back the union that was declared, which is vacuous with respect to whether that union is a shape `theme.Assembler` could produce from the declared entries. So the fixture set holds a hand-maintained copy of three production rules — membership (built-ins ∪ files ∪ unresolved persisted slugs), one-slug-one-row dedup, and `rowBefore`'s fold-then-bytes-then-built-in-first ordering — in the one place the project has designated as the sole pre-release visual-verification route. Membership, dedup, ordering, `Count` and `Rejected` then come from the production assembly, and each fixture states only what it is testing. If deriving is rejected, add a test that asserts each declared union equals what `Assembler` produces for that fixture's entries and keys, so the duplicate cannot drift silently.

- FINDING: `theme.AdaptivePair`'s tagged-palette machinery is three exported symbols guarding one in-package call
  SEVERITY: low
  FILES: internal/theme/member.go:26-36, internal/theme/nomination.go:32-45, internal/theme/resolution.go:162

- FINDING: `Rejection.Tokens` carries two different element shapes depending on `Reason`
  SEVERITY: low
  FILES: internal/theme/validate.go:41-65, internal/theme/validate.go:70-86, internal/theme/events.go:150-159, internal/theme/reason.go:27-34
  DESCRIPTION: For `missing tokens` the slice holds bare token names (`"text.primary"`); for `bad colour` it holds pre-rendered offender pairs (`"text.primary = #GGGGGG"`). Both flow unchanged through `tokenAttr` into a log attr named `token`, so half the time the `token` attr's value is not a token. The field is documented as "the structured source behind Detail", but for `bad colour` it is already rendered copy, which is the thing the surrounding code is careful to keep out of structured fields (`tokenAttr`'s own comment says it "never parses Detail" for exactly this reason). Any consumer added later that wants the offending token names — a panel highlight, a doctor grouping, a `count` of affected tokens — gets a formatted pair and has to re-split it, which is the parse the design is trying to prevent.
  RECOMMENDATION: Keep `Tokens` as token names for both reasons and carry the offending values alongside (a parallel `Values []string`, or a small `{Token, Value}` pair slice), formatting `"%s = %s"` where `Detail` is composed. `tokenAttr` then joins names for both reasons and the attr matches its name.

- FINDING: Two panel fixtures are exact clones distinguished only by a render size the `Fixture` type cannot express
  SEVERITY: low
  FILES: internal/capture/fixtures.go:498-505, internal/capture/fixtures.go:618-625, internal/capture/harness.go:22-42, internal/capture/theme_swap_guard_test.go:313-350
  DESCRIPTION: `theme-panel-narrow` and `theme-panel-min-height-message` return their base fixtures with only `name` changed; the state that makes them the frames the design calls for — minimum panel width, and the height floor with a message live — is terminal geometry, which lives in the caller (`ModelAt(th, w, h)`) and, during implementation, in a `.tape` that is scaffolding and gets cleared. Every Go-side consumer renders all fixtures at one fixed `harnessWidth`/`harnessHeight`, so these two produce byte-identical output to their bases: they add nothing to the swap-and-diff guard while being counted by its fixture enumeration, which inverts the property the guard leans on (a fixture's presence reading as coverage). Once the tapes are gone, the geometry survives only as a prose comment.
  RECOMMENDATION: Give `Fixture` an optional declared render size (zero meaning "the caller's size") and have `ModelAt` and the guard honour it. The two fixtures then differ in data rather than in an external instruction, they render their intended frames from any Go-side consumer, and the geometry stops depending on an artifact the retention rule deletes.
