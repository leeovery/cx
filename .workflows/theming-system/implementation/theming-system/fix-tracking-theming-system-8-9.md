ISSUES:

- **Production `Ctrl+↑`/`Ctrl+↓` do not page — they step one row, so they are behaviourally identical to `↑`/`↓`.** `internal/tui/theme_panel.go:423` sizes the model's list to `themePanelMinBodyRows` (1), while `renderThemePanel` (`theme_panel.go:720`) sizes its own per-frame COPY to the real body height. Measured through the production `t` keypress at 100x28: model list height=1, `Paginator.PerPage`=1, TotalPages=6, while the rendered copy gets 20 body rows. `bubbles/list.updatePagination` (`list.go:793`) computes `PerPage = max(1, availHeight/delegateHeight)`, so a one-row-high list has a one-row page and `NextPage()` advances the index by exactly 1.

  This is why `sizeArrowPanelList` (`theme_panel_arrow_test.go:168`) is **load-bearing rather than cosmetic**: `TestPanelArrow_SkipComposesWithPaging`'s fixture (perPage=2, invalid row at index 2) is degenerate at PerPage=1 — `Ctrl+↓` from index 0 would land on index 1, a valid row, exercising no skip at all. The helper is honestly documented and the arm itself IS height-agnostic, so "the skip composes with paging" is fair as a claim about the mechanism; but **"`Ctrl+↑`/`Ctrl+↓` page it" is not fair as a claim about the build.**

  FIX (recommended): in `applyThemePanelListStyles` (`theme_panel.go:422-425`) size the model's list from the same arithmetic the renderer uses rather than from the floor — `width, rows := themePanelListSize(m.themePanel, m.contentHeight()); m.themePanel.list.SetSize(width, rows)`. `themePanelListSize` is already pure and already the renderer's own function, and `overlayThemePanelOnContent` is called with `contentH == m.contentHeight()` (`model.go:4365, 4394`), so the model's page and the drawn page agree exactly with no new geometry decision invented here. Then drop `sizeArrowPanelList` from `TestPanelArrow_NavigationBindings` and `TestPanelArrow_SkipComposesWithPaging` so both observe the production page size (size the fixture terminal instead, via `arrowTermH`), and keep an assertion that `Ctrl+↓` moves the cursor by more than one row.

  ALTERNATIVE (not chosen): leave the sizing to 8-11 and explicitly re-home this acceptance criterion there, amending 8-11's "Do" to size the model's list at OPEN as well as on `tea.WindowSizeMsg` — its current Do only covers the resize path, so a panel opened without a subsequent resize would stay at PerPage=1 and the defect would survive the phase. Tradeoff: no code churn now, but it defers a one-line fix behind a plan amendment and leaves a shipped state where a documented key does nothing distinct.
