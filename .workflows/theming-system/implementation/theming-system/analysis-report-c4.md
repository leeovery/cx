# Analysis Report: theming-system (Cycle 4)

## Stats

- Total findings: 18 (architecture 6, duplication 8, standards 4)
- Deduplicated findings: 18 (no cross-agent duplicates this cycle — the three agents landed on disjoint surfaces)
- Proposed tasks: 14

## Summary

The three agents agree the subsystem is structurally sound: `internal/theme` is a genuine leaf owning the vocabulary, ladder, resolution and row assembly with path and emission policy both injected, the production code is unusually well single-sourced, and the implementation reads as a faithful execution of the specification. What remains is refinement in three bands — one high-severity test-surface duplication (the 19-token synthetic swap-probe palette authored independently in `internal/capture` and `internal/tui`, where a 20th token would silently void both halves of the theme-swap guard), a cluster of copied test bodies and re-implemented source-guard scaffolding written across task boundaries, and a documentation gap where this feature's headline public contract — the token rename — was applied to code but never to the render layer's own comments (328 production and ~446 test references to retired token names survive across `internal/tui` and `internal/capture`).

One medium architecture finding was narrowed rather than taken whole. The commit path's discarded slot resolution has two halves: gating the in-force light/dark answer on it (a real coupling — a failed palette load silently pins a light terminal to the dark slot for the session) and collapsing `ResolveSlot` off the `ThemeSource` seam. Task 3 takes the first; the second was dropped because `internal/theme` documents the two-entry-point split as deliberate ("separate methods rather than a flag so that pairing is stated in a type and a later call site cannot pair them the other way round") and cycle 3's task 13-10 already weighed the seam's four-method count and chose rename-not-split.

## Discarded Findings

- **`themeState.nomination` is maintained past construction with no production reader** (architecture, low) — settled. Cycle 3's task 13-9 raised exactly this; the user reviewed it and decided to KEEP the commit-time assignment and make the field's stated contract honest instead. That landed (commit 9b7d092f), and `theme_state.go:20-32` now documents the field as kept consistent with the persisted setting at one site. Re-proposing the drop would reverse an explicit user decision.
- **`prefs.ThemeKeys` → `theme.RawKeys` crosses the boundary as three positional strings at two sites** (architecture, low) — settled, no new argument. Cycle 3's task 13-4 addressed the transposition hazard, moved `ResolveSetting` to take the typed value, and deliberately left the two `cmd` prefs-boundary sites positional because `internal/theme` must stay a leaf and the boundary genuinely holds three loose strings; a reviewer confirmed that shape. This cycle's finding restates the same hazard and recommends a `cmd`-local named conversion — a variant the prior task's scope already considered — without weighing anything the prior task did not.
- **The panel's block assembly re-authors the clamp / pad-to-width / blank-fill loop** (duplication, low) — discarded on shape. `themePanelBlock` legitimately adds the border/gutter prefix and the above-the-rule region split, so it is a near-duplicate, and the finding's own recommendation leaves the two pre-existing Modern Vivid sites (`fillCanvas`, `fillColourless`) to adopt the primitive "as they are next touched". Extracting for the one converted consumer produces indirection rather than de-duplication, and converting the pre-existing MV sites is outside this implementation's surface.
- **Spec-section citations in new test comments** (standards, low) — discarded as re-work on a settled convention. This was already tasked twice (cycle 1 swept production, cycle 2's task 12-8 swept the topic's test comments) and has recurred in files that sweep covered, which shows a sweep without a guard does not hold; a guard is not constructible while 202 pre-existing test files carry the same convention. The finding itself notes it is an established codebase convention rather than a new practice and explicitly declines to recommend a rewrite.
