SPEC CONTEXT:
Spec §14A (`specification.md:1816-1823`) lists the notice band's order as *filter line → burst progress → transient flash → multi-select banner → unsupported banner → no-tags signpost*, routes all six theme signals through the transient-flash slot, and then decides that "the filter line is the one contender above flash that can be live throughout a panel open/use/close, and the theme flashes take precedence over it" — naming it a change to the band's precedence. The two guarantees it protects are §9.13's failed-commit report (raising discharges the state, so a suppressed flash is destroyed, not deferred) and §9.10's proactive `NO_COLOR` block (suppression would produce nothing at all). §14A also grants Projects the flash contender alone.

The spec's premise is factually wrong about the implementation: the filter line is not a band contender. `applySectionHeader` (`internal/tui/model.go:3326-3375`) and `applyProjectsSectionHeader` (`model.go:3151-3169`) render the filter query by replacing the list's **title row**, while the band renders in `renderSessionBandSlot` / `renderProjectBandSlot` — a different physical row. The behaviour §14A requires therefore holds structurally, which is precisely what this task exists to document and pin.
