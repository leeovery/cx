- FINDING: A second, unspecified lock bound and a new exported read method were introduced
  SEVERITY: medium
  FILES: internal/hooks/lock.go:24-26, internal/hooks/store.go:44-53, internal/hooks/locktest.go:24-31, cmd/run_hook_stale_cleanup.go:100
  DESCRIPTION: The specification declares exactly one acquisition bound — "The bound is 2 seconds ... a package-level value the unit lane can lower" — and has the sweep's advisory pre-read degrade "by the same rule" as every other read. The implementation adds a second bound, `snapshotLockTimeout = 20 * time.Millisecond` (100x shorter), reachable only through a new exported `Store.LoadSnapshot(via)` method and a second test seam `SetSnapshotLockTimeoutForTest`. The stated rationale — one sweep cycle takes the sidecar twice, so at the full bound a wedged writer would park the daemon's 1s tick for two full bounds — is sound and serves the spec's own intent, but the spec already reasoned about exactly this stall in §6.3 and resolved it by releasing the shared hold before `CleanStale` rather than by adding a bound. This is a design decision made at implementation time, not one the specification made, and it widens the store's public surface (a second read entry point that a future caller can pick by accident) and the tuning surface (two constants that can now drift). Behaviourally it is benign — a pre-read that cannot acquire in 20ms just degrades to an unlocked read with a DEBUG breadcrumb, which the spec sanctions — so the concern is the undiscussed decision and the extra API, not a correctness break.
  RECOMMENDATION: Confirm the second bound is wanted. If it is, it belongs in the spec's §6.5 bound paragraph alongside the 2s figure and its justification, so the two values stay explained together. If it is not, collapse `LoadSnapshot` back onto the single `lockTimeout` and delete `snapshotLockTimeout` / `SetSnapshotLockTimeoutForTest`, keeping the release-before-`CleanStale` ordering the spec relies on.

- FINDING: The reaper's per-key INFO deletion lines are emitted before the write that performs the deletion
  SEVERITY: low
  FILES: internal/hooks/store.go:296-305
  DESCRIPTION: `CleanStale` logs one `clean-stale` line per candidate key, then calls `s.save(kept)`. When the save fails the keys are still in the file, but the log has already named each of them as removed. This ordering predates the work unit, but it was harmless while the line was DEBUG; the specification promotes it to INFO precisely so that "what did I lose?" is answerable from the production-default log, and a line claiming a deletion that did not happen is the same class of misleading record the work unit exists to remove. The batch summary does carry the save error, so an operator who reads both lines can reconstruct the truth — but the per-key line is the one the spec added for standalone forensic value.
  RECOMMENDATION: Move the per-key INFO loop below the successful `s.save(kept)` call, leaving the failure path to emit only `storelog.EmitCleanStaleSummary(..., err)`.
