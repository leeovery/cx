ISSUES:
- `internal/hooks/store.go:79,132,228` — the no-nesting invariant has zero enforcement, and it is the one invariant this task calls its riskiest. Acceptance criterion 8 says "`Set`, `Remove` and `CleanStale` use only the unexported `load`/`save`". The code satisfies it; nothing checks that it keeps satisfying it. Proven: rewriting all five `s.load()` calls to `s.Load()` leaves the **entire package suite green** (`ok … 0.730s`). It passes today only because `Load` does not yet lock — which is precisely what task 5-2 changes. At 5-2 a nested `Load` takes `LOCK_SH` on a second file description, blocks against the mutation's own `LOCK_EX` for the full 2s, then degrades to an unlocked read and logs at DEBUG. So the regression would not fail the suite even then: it would silently make every `hook set`, `hook rm` and daemon sweep take 2s+, and the only detector in the whole package would be `lock_test.go:293`'s Set-only timing subtest. For contrast, a *literal* second `acquireMutationLock` in `Remove`/`CleanStale` IS caught loudly (mutation-verified — the whole Remove/CleanStale suite fails at the bound). It is specifically the exported-front-door route that is invisible.

Extend that file with a sibling — walk the same parsed files, and for `funcName` in {`Set`, `Remove`, `CleanStale`} error when `calleeName(call)` is `Load` or `Save` on an `s` receiver — plus the existing `if scanned == 0 { t.Fatal }` vacuity check. ~15 lines, no new helper, no timing, catches the regression today rather than at 5-2.
  ALTERNATIVE: table-drive `lock_test.go:293`'s `"it acquires exactly once per mutation"` over all three methods against the lowered bound. Cheaper to write and it does catch a literal double-acquire, but it is a wall-clock assertion that stays blind to the exported-`Load` route until 5-2 lands, and blind altogether if 5-2's degraded-read path swallows the block. The source guard is deterministic and catches both routes now — reviewer recommends it.

- `store.go:229` — `start := time.Now()` now precedes the acquire, so the `clean-stale` summary's `took` includes lock-wait time under contention (up to 2s). Defensible and arguably more useful, but it changes what a slow `took` in portal.log means. On acquire failure no summary is emitted at all, which is correct for this task's scope.
- `lock_test.go:304` asserts `elapsed < bound/2` (50ms wall clock) for an uncontended `Set`. Packages run in parallel in the unit lane, so that is a 50ms budget for open + flock + read + marshal + rename with only 2× separation from the failure mode. It passed every run, but a wider margin (assert against `bound` with a larger `bound`) would remove the flake surface without weakening the signal. **Optional — take it if it costs nothing.**
