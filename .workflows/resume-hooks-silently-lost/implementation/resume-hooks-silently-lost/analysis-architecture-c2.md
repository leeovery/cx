- FINDING: The generated-id width is now a hooks.json on-disk contract but is shaped and documented as a generic generator knob
  SEVERITY: medium
  FILES: internal/nanoid/nanoid.go:22, internal/nanoid/nanoid.go:47, internal/hooks/store.go:251, internal/session/naming.go:14, internal/spawn/burst.go:58, cmd/open.go:414
  DESCRIPTION: `nanoid.width` is read by three unrelated id domains — session-name suffixes (`session.GenerateSessionName` via `IDGenerator`), spawn batch/ack ids (`spawn.NewSpawnID`, `burst.go`), and pane tokens (`session.NewPaneToken`) — and by `IsTokenShaped`, which the reaper uses to decide whether a persisted `hooks.json` key may be deleted at all. That makes `width` a persisted-format constant, not a generator knob, yet its doc comment scopes the coupling narrowly ("read by both the generator and IsTokenShaped, so generation and recognition cannot drift apart") and says nothing about the other two consumers or about disk. Change the width for an unrelated reason — longer session-name suffixes to reduce collisions, say — and every six-character token already in `hooks.json` stops being token-shaped, so the reaper retains it forever, `checkStaleHooks` (which counts through the same shape rule) keeps reporting "no stale hooks", and `portal doctor` stays green while the file accumulates entries no pane answers to. That is the same class of silence this work unit exists to remove, arriving through a different door. `hookstest.ReapableHookKey` panics on a width change, so the *fixture vocabulary* fails loudly — but nothing in the suite exercises a persisted key authored under the old width, so once the fixture is repaired the data-classification change is invisible. The spec's argument for deriving the predicate from the generator's constants assumed those constants belonged to the pane token; consolidating three domains onto one width widened the blast radius past what that argument covers.
  RECOMMENDATION: Make the on-disk contract explicit at the constant. Either state in `internal/nanoid`'s package doc and above `width` that the value is part of `hooks.json`'s key-recognition contract and that changing it reclassifies every persisted key (so a change is a migration event, not a tuning change), or give the pane token its own named width beside `IsTokenShaped` that both the pane-token mint and the predicate read, leaving session-name and spawn-id widths free to move independently. The second keeps the spec's no-drift property while narrowing the coupling back to the one domain that has durable storage.

- FINDING: CleanStale's enumeration callback carries its decline reason out-of-band through a captured variable
  SEVERITY: medium
  FILES: internal/hooks/store.go:302, cmd/run_hook_stale_cleanup.go:165, cmd/run_hook_stale_cleanup.go:173, cmd/run_hook_stale_cleanup.go:197
  DESCRIPTION: `Store.CleanStale(enumerateLive func(Snapshot) ([]string, error))` documents that a returned error "is returned unwrapped, so a caller can carry its own reasons through" — an invitation to put the reason in the error. The only caller does not: `runHookStaleCleanup` returns the bare sentinel `errCycleDeclined` from the closure while writing the actual reason, level and attrs into a `decline standDown` variable captured from the enclosing scope, and `declinedSweep` re-joins the two afterwards. The sentinel and its payload are two independent channels that must be kept in step by hand. A second decline path added inside that closure that returns `errCycleDeclined` without assigning `decline` yields the zero `standDown`: `emit()` writes `hooks: clean-stale-skipped reason=` at INFO with an empty reason, and `sweepOutcome{DeclineReason: ""}` is indistinguishable from a cycle that ran and found nothing — so `portal doctor --fix` prints no skip line and the daemon reports nothing. Correctness here rests on caller discipline at a package boundary rather than being self-contained, which is the property this work unit spent §4 and §5 removing everywhere else.
  RECOMMENDATION: Fold the reason into the error so the two cannot separate — a small typed error in `cmd` wrapping the `standDown` (`type declinedError struct{ standDown }`), returned from the closure and recovered in `declinedSweep` with `errors.As`. `errCycleDeclined` and the captured `decline` then both disappear, and `CleanStale`'s documented "carry your own reasons through" contract is actually the mechanism used.

- FINDING: Pane-identity minting is homed in the session-creation package as a vestigial forwarder
  SEVERITY: low
  FILES: internal/session/panetoken.go:8, cmd/hooks.go:44, cmd/hooks.go:100, cmd/open.go:414
  DESCRIPTION: `session.NewPaneToken` is a ten-line pass-through to `nanoid.NewGenerator()()` with one production caller, and `HooksDeps.TokenMinter` is typed `session.IDGenerator`, itself an alias of `nanoid.Generator`. So `cmd/hooks.go` imports `internal/session` — documented as the session creation pipeline (git root → project persistence → name generation → tmux session creation) — solely for a type alias and a forwarder that concern pane identity, which has nothing to do with sessions. Two conventions for one thing, and the one that goes through `session` puts pane identity in a package whose role the repo's own architecture description scopes elsewhere. The wrapper exists because the spec placed the token generator and shape predicate together in `internal/session`; extracting `internal/nanoid` (the right call — it is what keeps `internal/hooks` a stdlib-plus-leaves package, and the leaf guard pins that) removed the reason for the wrapper but the wrapper stayed.
  RECOMMENDATION: Type the seam as `nanoid.Generator` and default it to `nanoid.NewGenerator()`, deleting `internal/session/panetoken.go` and the `internal/session` import from `cmd/hooks.go`. Both id-minting call sites in `cmd` then read the same way, and pane identity stops living in the session package.

- FINDING: runHookStaleCleanup's injected logger governs only part of its output
  SEVERITY: low
  FILES: cmd/run_hook_stale_cleanup.go:51, cmd/run_hook_stale_cleanup.go:153, cmd/run_hook_stale_cleanup.go:169, cmd/run_hook_stale_cleanup.go:189
  DESCRIPTION: `runHookStaleCleanup(reader, store, logger *slog.Logger)` takes a logger, defaults it to `bootstrapLogger` when nil, and uses it for exactly two DEBUG count lines. Every stand-down line — the ones that answer the question the sweep's observability exists for, "did the prune decline and why" — is written by `standDown.emit()` to the package-global `hooksLogger`, bypassing the parameter entirely. A caller that injects a logger to observe the sweep captures the counts and none of the stand-downs; the test suite works around this by additionally installing a global handler via `logtest.Install`. The split is defensible on component grounds (the stand-down must carry the `hooks` component, the counts carry the caller's), but the signature advertises injectability it only partly honours, and nothing at the call site says so.
  RECOMMENDATION: Either name the parameter for what it actually governs (e.g. `countsLogger`) and state in the doc comment that stand-downs are emitted under the `hooks` component regardless, or drop the parameter and bind the counts to the component they belong to — the two call sites pass `deps.Logger` and `bootstrapLogger`, neither of which needs to be a parameter for a DEBUG count line.

- FINDING: Two unlinked reason-to-phrase maps in doctor, neither exhaustive over the reason constants
  SEVERITY: low
  FILES: cmd/doctor.go:215, cmd/doctor.go:308, cmd/run_hook_stale_cleanup.go:16
  DESCRIPTION: `skippedPrunePhrases` (five entries) and `notEvaluableDetails` (four) both key off the same `skipReason*` const block declared in another file, render it in two registers, and both fall through to the raw slug when a reason is unmapped. Nothing binds either map to the const block, so adding a sixth reason compiles and ships, and the user sees the internal slug (`store-read-failed`) in `portal doctor` output. The fall-through is documented as deliberate — better than printing nothing — but it converts a missing entry from a build error into a cosmetic production defect, on the command whose whole purpose is telling the user what happened.
  RECOMMENDATION: Home the phrases with the reasons: give the reason a small type (or move both maps beside the const block) and add a table-driven guard asserting every declared reason has an entry in each renderer. That keeps the fall-through as the runtime safety net while making the omission fail at test time instead of at the user.

- FINDING: logtest's Records filter methods are exported but never chained by any consumer
  SEVERITY: low
  FILES: internal/logtest/capture.go:82, internal/logtest/capture.go:86, internal/logtest/capture.go:91, internal/logtest/capture.go:96
  DESCRIPTION: The new `Records` named slice type exports three chainable filters (`AtExactLevel`, `AtOrAboveLevel`, `With`) alongside three `Sink` forwarders (`RecordsAtExactLevel`, `RecordsAtOrAboveLevel`, `RecordsWith`) that call them. Across the whole repository the chained form is used zero times outside the package; every consumer goes through a `Sink` forwarder. `logtest` is a shared helper imported from cmd, state, restore, tui, tmux and the store suites, so its exported surface is a contract several packages read — and half of it is a second way to do what the other half already does, kept alive only by its own forwarders.
  RECOMMENDATION: Unexport the three filter methods (or make them plain unexported functions over `[]Record`) and keep `Records` as the return type. The `Sink.Records*` accessors stay identical for every existing caller and the package stops advertising an unused idiom.
SUMMARY: The structure is strong — `internal/nanoid` as a stdlib-only id vocabulary, `internal/hooks` held to a guarded leaf boundary, one staleness rule reached by both the sweep and the diagnostic, and a real-tmux-through-reboot-to-hook-fire integration path covering the whole chain. Two issues are worth acting on: the shared id width has quietly become part of `hooks.json`'s on-disk recognition contract without being documented or guarded as one, and the sweep's decline reason travels beside its sentinel error rather than inside it, so a future second decline path would report a stand-down as an ordinary empty cycle.
