- FINDING: CleanStale's contract puts an ordering invariant and two interchangeable slice arguments on the caller
  SEVERITY: medium
  FILES: internal/hooks/store.go:295, cmd/run_hook_stale_cleanup.go:103, cmd/run_hook_stale_cleanup.go:141
  DESCRIPTION: `CleanStale(liveTokens, snapshotKeys []string)` takes two adjacent `[]string` parameters whose roles are inverses of each other — one is "keys that must be protected", the other is "keys that may be considered" — and the correctness of the whole anti-reap protection depends on a temporal fact the signature cannot express: `snapshotKeys` must have been read *before* whatever enumeration produced `liveTokens`. That fact lives only in a comment at the single call site (`cmd/run_hook_stale_cleanup.go:95-102`).

  Two failure modes follow from the shape. A transposed call (`CleanStale(snapshot, tokens)`) compiles and type-checks, and its effect is not benign: it computes staleness against the snapshot and narrows to the live set, which can delete entries whose panes are alive — the exact loss the work unit exists to prevent. And any second caller, or a reorder of the two reads at the existing one, silently inverts the protection with nothing failing: `cmd/hook_sweep_snapshot_order_test.go` pins the ordering at *this* call site behaviourally, but nothing pins it for the API.

  RECOMMENDATION: Make the store own the sequence rather than document it. The cleanest form is to have `CleanStale` take the live-token producer as a function — `CleanStale(enumerate func() ([]string, error))` — so the store reads its own advisory snapshot, releases the shared hold, calls `enumerate` with no lock held (which also enforces the "no tmux inside the lock" rule structurally instead of by convention), then takes the exclusive hold and derives. The sweep's empty-row guard rides along by having the closure return a sentinel error. If a callback is unwanted, the cheaper fix is a named type for the snapshot (`type Snapshot []string`, returned by `LoadSnapshot` rather than a bare map) so the two arguments stop being interchangeable at the type level.

- FINDING: Not every way the sweep declines to run reaches the caller, so `doctor --fix` can print nothing at all
  SEVERITY: medium
  FILES: cmd/run_hook_stale_cleanup.go:103, cmd/run_hook_stale_cleanup.go:109, cmd/doctor.go:200, cmd/doctor.go:213
  DESCRIPTION: `runHookStaleCleanup` has five outcomes in which no pruning happens: restore window set, empty pane read, lock timeout, `LoadSnapshot` failure, and `ListAllPaneHookKeys` failure. Only the first three call `reportSkip`. The two read failures return (`err` and `nil` respectively) having invoked no callback — and `pruneDoctorStaleHooks` discards the return with `_ =`. So a `portal doctor --fix` whose pane enumeration errors prints neither a `Pruned stale hook:` line nor a `Skipped stale hook prune:` line: the repair silently did not run, which is the class of silence this work unit exists to remove. The vocabulary for it already exists — `skippedPrunePhrases[skipReasonEmptyPaneRead]` reads "could not read live panes", which describes a *failed* read better than the successful-but-empty read it is actually wired to. The sibling repair `pruneDoctorStaleProjects` at least logs a WARN on its error path; the hook prune does not.

  The root cause is the callback shape: `runHookStaleCleanup(lister, store, logger, onRemoved, onSkipped) error` has five parameters, two of them optional callbacks (the daemon passes `nil, nil`) plus an `error` return, so "what happened this cycle" is spread across four out-channels and one caller can only observe three of them. It also splits its emissions across two loggers — the injected `*slog.Logger` for the two read failures and the package-level `hooksLogger` for the three stand-downs — so `grep "hooks:"`, the grep the closed `op=clean-stale-skipped` vocabulary was introduced for, answers "did the prune stand down and why" for three of the five cases and misses two.

  RECOMMENDATION: Collapse the out-channels into one value: `runHookStaleCleanup(lister, store, logger) (sweepOutcome, error)` where `sweepOutcome` carries the removed keys and, when the cycle declined, the reason. The daemon ignores it, `doctor --fix` renders both halves, and a newly added decline path cannot be forgotten because it has to populate the same field the renderer already reads. Fold the two read failures into that reason set (the log line can stay under whichever component is right) so both surface to a user who asked for a repair.

SUMMARY: The hook-key rewrite lands cleanly — one home for the option literal, one implementation of the staleness rule, mutations properly serialised behind a sidecar lock, and genuinely strong end-to-end coverage of the reboot and moved-pane paths. The structural weaknesses are at the boundaries: a leaf persistence package that now transitively depends on the tmux client to reach a ten-line predicate, a `CleanStale` contract whose central ordering invariant is held by a comment and whose two same-typed arguments are transposable, a sweep whose "nothing happened" report covers three of its five decline paths, and a test-helper package accreting unrelated subjects.
