Twelve of thirteen acceptance criteria met; the production code is correct — **do not change it**. The headline ordering fix, the intersection, the no-lock-during-enumeration proof, the short bound and the empty-snapshot early return were all mutation-verified and hold. One test does not pin the criterion it is named for, and is weaker than the form it replaced.

ISSUES:
- `cmd/hook_sweep_snapshot_order_test.go:88-134` — `"it feeds onRemoved exactly what was deleted"` does not pin its criterion. It measures the callback against a **file delta**, and in this fixture the file delta, `CleanStale`'s returned slice, and a call-site prediction all coincide, so the assertion cannot tell them apart. Proven: replacing `for _, name := range removed` with `for _, name := range hooks.StaleKeys(persisted, tokens)` at `cmd/run_hook_stale_cleanup.go:146` — feeding the callback the call-site prediction, the exact thing the criterion forbids — leaves the **entire `cmd` package green**, unit and integration lanes both. The criterion's stated stake is that `doctor --fix` never prints `Pruned stale hook:` for a removal that did not happen (`cmd/doctor.go:200`), and that failure mode currently ships unguarded.
  **The rewrite made it weaker, not stronger.** The RED you reported came from the ordering fix, not from callback fidelity, so the tightening removed the only thing making the test fail without adding what it claims to add. The comment at `:118-119` ("a key created and then reaped mid-run is a deletion the callback must have named") justifies the measure by a scenario the corrected implementation makes impossible — a key created after the snapshot can never be reaped — which is why the measure has nothing left to discriminate.
  FIX: make the fixture produce a genuine divergence between the snapshot and the file under the lock, and assert the callback against the exact expected set rather than a delta. Seed `{liveSeedA, reapableSeedB, reapableSeedC}`; have `during` call `store.Remove(reapableSeedC, "on-resume", "cli")` — another writer removing a key the snapshot holds — with `rows: tokenRows(liveSeedA)`; assert `reported` equals exactly `[]string{reapableSeedB}`, because C's removal was the other writer's, not the sweep's. The reviewer ran this both ways in a throwaway copy: it passes against the committed implementation and fails against the mis-feed mutation with `onRemoved reported [reapab reapac], want only [reapab]`. Keep or fold in the existing mid-run-registration case if you want both windows covered, and **replace the `:118-119` comment**, which no longer describes the measure.
  ALTERNATIVE: have `runHookStaleCleanup` return the removed slice and assert callback-equals-return directly. That is the literal reading of the task's test text and the strongest possible pin, but it widens a production signature for a test's benefit and both callers discard the value. The reviewer recommends the fixture-divergence form.
  CONFIDENCE: high
