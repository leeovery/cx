# Shard sessions across multiple tmux servers

The tmux server is single-threaded: one process, at most one CPU core, one thing at a time off an event loop. With 20–30+ Claude sessions streaming heavy output, the server thread becomes the choke point — observed at ~90% CPU during a recent slowdown, with keystrokes and scrolling queuing behind background output. The workload profile makes this structural: the system runs 24/7, several sessions stream at once (Claude output, dev servers), remote clients attach from mobile/iPad, and Portal's own saver daemon capture ticks through the same thread. Sharding won't reduce total machine CPU (the Claude processes themselves already spread across cores) — it removes the single-core ceiling on the interactivity layer.

The idea: Portal manages N tmux servers and places sessions across them, governed by one knob — `max_sessions_per_server`. Cap=1 gives the screen/zellij per-session-server model; cap=4–6 gives sharding. Placement stays simple: least-loaded server under cap, else start a new one; servers drain naturally as sessions die. No auto-scaling or pre-warming. Migration between shards is deliberately later scope, but Portal uniquely could do it: kill + resurrect on another shard + resume hook relaunches `claude --resume`. Prior art: no tmux sharding manager exists, but the architecture is proven (GNU screen, abduco, zellij are per-session-server; wezterm went multithreaded instead). A Zellij port of Portal was discussed and parked as a separate question.

Discovery from a codebase scan (hypotheses to re-validate in research):

- The client binds to a server purely via ambient `TMUX` — no `-L`/`-S` anywhere in production. `Commander` is the natural seam, a socket-scoped commander is already proven in `tmuxtest.socketCommander`, and there are only ~10 client construction sites with one root injection point (`cmd/bootstrap_production.go`).
- The daemon inherits `TMUX` from its `_portal-saver` pane, so per-shard daemons work nearly unchanged — self-supervision, kill-barrier, and per-directory `daemon.lock` all stay scoped correctly. Decision leaning: per-server daemons, not a singleton (a singleton means evicting the daemon from tmux and rebuilding supervision).
- Known snags: the machine-wide `pgrep` orphan sweep can't distinguish shard daemons (argv needs a shard discriminator); the log subsystem owns the state-dir root and must split from per-shard state roots; `switch-client` can't cross servers — cross-shard switch needs the `detach-client -E` re-attach trick.
- Free wins: session names are already globally unique (`{project}-{nanoid}`), resume hooks are keyed by `@portal-id` (server-agnostic), and shard topology can be ephemeral — reboot restore just re-places sessions by policy rather than persisting which shard they lived on.
- Sizing: epic-scale, comparable to multi-window spawn or theming. Roughly 40% production code, 60% test infrastructure — the `TestMain` `TMUX`-poison isolation enforcement is bypassed by explicit socket args and needs rethinking, and the integration lane assumes one server throughout.

Before committing: verify the bottleneck next time the machine degrades — check whether the tmux server process itself is pegging its core, and how much of that load is the saver capture loop versus interactive traffic.
