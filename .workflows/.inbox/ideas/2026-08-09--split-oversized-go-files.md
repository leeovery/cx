# Split Portal's oversized Go files along their concern seams

Several files have grown far past the point where they read as one unit. The worst offenders: `internal/tui/model.go` at 5,467 lines with `internal/tui/model_test.go` at 7,766, `internal/tmux/portal_saver_test.go` at 4,394, `cmd/open_test.go` at 3,858, `internal/tmux/tmux_test.go` at 3,391. `model.go` in particular has become the TUI's everything-file — model state, update routing, view composition, and the wiring for each panel all live in one place, so nearly every TUI-adjacent change lands in or around it.

There is measured evidence that the size is an active cost, not just an aesthetic one. During the theming-system feature, `model.go` was the single most-read artifact in the entire implementation: 327 reads across 85 distinct implementation subagents — every executor and reviewer whose task touched the TUI had to page through it (a full pass is ~3 chunked reads at agent tooling's 2,000-line window). Hub-file gravity also concentrates merge risk: any future parallelism in implementation is dead on arrival while one file is the junction for half the feature surface.

Go makes the mechanical part cheap: files within a package can be split freely with zero API change — no import, caller, or test updates needed when the split stays inside the package. The work is choosing the seams, and the existing `theme_panel.go` / `theme_panel_commit.go` / `theme_row.go` siblings already show the pattern working in this package: panel-scoped files that keep their concern's model fields, update arms, and rendering together. A `model.go` split would continue that — peel each remaining panel/page's arms and view code into its concern file, leaving `model.go` holding the model struct, construction, and top-level routing. The giant `_test.go` files likely follow the same seams (Go test files in one package can also split freely), which matters because `model_test.go` at 7,766 lines is even less navigable than the production file.

Worth doing before or alongside the planned comment-cleanup sweep — smaller files shrink each cleanup agent's blast radius, and the two passes touch the same lines, so sequencing them avoids double churn.
