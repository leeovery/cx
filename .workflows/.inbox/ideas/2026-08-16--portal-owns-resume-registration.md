# Portal should own the resume-registration lifecycle, not an external shell hook

Today Portal owns half of resume: it stores per-pane on-resume commands in `hooks.json` and fires them from the hydrate helper after a reboot. The other half — deciding *what* command a pane should resume with, and keeping that current as the pane's work changes — lives entirely outside Portal, in a user-authored shell script wired into Claude Code's SessionStart/SessionEnd events (`~/.dotfiles/home/.claude/hooks/portal-resume-hook.sh`). Portal is a dumb key-value store for a string another program computes.

That split is where the fragility lives. The external script has to reverse-engineer things Portal already knows or could know: which pane it is in, whether the session it is reacting to is the pane's real session or a nested/subagent one, whether the directory it captured is the directory the tool actually anchors its state to. Every one of those has produced a real failure. Sessions have silently lost their resume registration for weeks; hooks have pointed at directories where the target no longer resolves; failed registrations have reported success. None of it is visible until a reboot, which is the worst possible time to discover it.

The idea is to move that ownership inward. Portal already tracks the durable identity of a pane (`@portal-id`, the hook key, the pane's directory) and already has a daemon running a capture loop over live panes. It is the natural place to observe what a pane is actually running and to keep a pane's resume intent accurate and self-correcting, rather than trusting a one-shot registration from an external process that may never fire again.

The obvious shape is Portal noticing the resumable work in a pane itself and maintaining the registration continuously, so a missed event, a clobbered entry, or a silently-failed write heals on the next observation instead of persisting until reboot. Whether that observation is process-based, a richer registration API a tool can call idempotently, or something the daemon reconciles on its tick is open.

Hard constraint: Portal's resume mechanism is generic and its UI, logs and vocabulary must never reference Claude or any specific tool. Claude Code is the driving use case and the source of every observed failure, but whatever lands has to be expressed in tool-agnostic terms — a pane has resumable work and a way to describe it — with Claude support being configuration or a shipped adapter rather than anything baked into Portal's model.

Relevant surfaces: `internal/hooks`, `cmd/hooks.go`, the hook-key primitives in `internal/tmux`, the daemon capture loop in `cmd/state_daemon.go`, and the hydrate exec chain that actually fires the stored command. Related inbox item: the `hook set` degenerate-key bug logged the same day.
